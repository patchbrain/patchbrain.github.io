Golang程序在运行时，goroutine作为Go运行的流程载体，会创建大量变量，并把数据存于其中，有的数据存在于Goroutine栈中，当Goroutine运行完毕时自动回收；但是有部分数据存在于Go堆中，这部分数据无法被自动回收。长期以往，如果不进行回收的话，这些数据就成了垃圾，占用着大量运行内存，从而影响程序执行效率。<br />针对这些垃圾，Golang不像C++等语言的手动回收机制（需要程序员适时通过代码进行回收），而是设计了自动的垃圾回收机制，通过追踪式GC进行高效回收，避免了手动管理的复杂和易错。
<a name="VegGY"></a>
# 何为追踪式GC
看到"追踪式"这三个字，就会马上浮现三个问题：

1. 追踪的目的是什么
2. 从哪里开始追踪
3. 追踪到哪里结束

问题1：追踪的目的是标记出程序还需要的对象，这些对象将不会被垃圾清扫程序清除掉。<br />问题2：从根节点开始追踪，根节点包括了程序确保会用到的数据，比如局部变量和全局变量。<br />问题3：所有可达对象及其引用对象都已经被扫描标记过。
<a name="r7MSR"></a>
## 三色标记法
三色标记法并非一种新的GC标记方法，只对追踪式GC进行具象化地解释。<br />将对象分为三种颜色：<br />白色：该对象还没有被追踪标记过。<br />灰色：该对象被追踪标记过，但是还需要追踪该对象所引用地对象。<br />黑色：该对象及其引用的对象都已经被追踪标记过。

追踪从根节点开始，遍历到的节点都置为灰色，除非该节点及其引用都已被扫描过则置为黑色，没有被着色的都为白色。根据标记规则不断执行，最后剩下的白色对象，就是需要被清扫的对象。
<a name="jwFiH"></a>
# GC周期
<a name="vE2ge"></a>
## 状态流转
Golang的GC算法被称为"标记-清扫算法"，这意味着至少有两种状态：标记状态和清扫状态。<br />并且，这两者在时间上必然是没有交叉的，如果没有标记完成，那么清扫就一定不可能发生，因为无法预知到如果标记未完成，是否会有一个指针引用着数据，但其颜色还是白色。如果它被清扫，有几率造成程序错误或业务错误。

另外，除了这两种状态，GC流程可能根本就不需要开始，因为可能没有和GC相关的对象被创建，或者通过控制参数将GC关闭了。<br />因此Golang GC一共有三种状态： 关闭、标记状态、清扫状态。
<a name="qlTwA"></a>
## 成本
> GC关注的内存由以下几个部分组成： 存活堆内存(上一轮GC确定的存活下来的堆内存)，新分配的堆内存(本轮GC周期内新申请的堆内存，它们可能会被标记为存活或者相反)，以及描述以上两个部分的元数据(占比小，可忽略)。

Golang运行时是复杂的系统，在梳理主要脉络时不宜沉浸在某个细节中，因此我们只关注最重要的两个成本项：GC占用的CPU时间(cpu time)以及Go程序的物理内存(physical memory)。<br />为了建立关于这两者关系的认知，我们拟定一个稳定状态，该状态假设golang运行时分配内存的速率是一定的，而且每个分配周期对象图的大小和深度都是一定的。<br />另外，即使在稳定状态下，活跃堆(某个时间点，在堆中被认为是活跃的内存量)可能相对于上一次GC结束会增长/减少/保持不变。为了简单清晰起见，就假设活跃堆的大小保持不变。<br />在以上情况下，如果每次GC的间隔也保持不变的话，GC的成本每次都是相等的。此时考虑将GC点往后移，那么程序会在更大的时间范围中分配更多的内存，但是每次GC周期使用的CPU时间是相同的，因此在一个时间窗口中，GC的次数会减少，即GC的CPU time会降低。 反之，GC频率升高，但是活跃堆大小也会减少，因为GC点前移，程序分配的堆大小会因分配时间减少而减少。<br />也就是说，调控GC的频率，就可以调控GC的CPU time和物理内存量的平衡，有两个控制参数可以进行这两个成本的平衡：GOGC和内存限制
<a name="u9buS"></a>
## 控制参数
<a name="TLHFK"></a>
### GOGC
GOGC是一个环境变量，可以直接用于控制到达下一次GC周期前允许的堆增长率。如果GOGC为100，则代表堆大小可以增长大约100%，具体公式如下：<br />![image.png](http://pic.kinghno3.top//kinghno3_blog/20240720030606.png)<br />公式中的GC Roots是在go1.18之后才引入的，目的是：<br />GC Roots包括了goroutine stack上分配的对象，对于Go堆中分配的对象来说只占很小一部分，但是如果在有成千上万的goroutine stack的情况下，这部分内存就无法忽视了。

GOGC也间接控制着GC的频率，从而控制着内存和cpu时间。<br />当GOGC较小时，能够运行的堆增长率也较小，因此更容易触发GC，从而将堆内存维持在一个较小的状态下，然而这会导致GC频繁，使用的cpu时间较多，甚至对程序运行效率造成明显的影响。  反之亦然。

以下是稳态下应用程序的堆内存变化图。其中参数GOGC为100，也就是新堆的大小与活跃堆大小相等时，将会触发GC。以2.0s之后为例，活跃堆稳定在20MB，当新堆大小达到20MB时将触发一次GC，总内存量重新回到20MB，所以，最后呈现均匀的锯齿状。<br />![image.png](http://pic.kinghno3.top//kinghno3_blog/20240720030634.png)
<a name="MHZIE"></a>
### 内存限制
在Go1.19前，只有GOGC这一个参数去作为权衡CPU时间与堆内存增长率的手段。GOGC并不会关注堆内存的绝对量，如果瞬时活跃堆峰值很高，那么GOGC也并不会对此做出恰当的反应，反而纵容活跃堆内存达到程序无法承受的量，甚至导致崩溃。如果要控制这种情况发生，就必须提高GC频率，但是只通过降低GOGC相对难以做出CPU时间与堆总量的平衡。<br />比如下图，如果容器限制应用程序堆大小为60MB，那么此处的GOGC就一定不能超过100。另外，有些应用程序的内存峰值是难以预测的，如果GOGC设置不当，就有可能出现崩溃等情况。<br />![image.png](http://pic.kinghno3.top//kinghno3_blog/20240720030649.png)<br />因此，需要对内存量做限制，GOMEMLIMIT这个环境变量便完成了这项工作。也可以通过SetMemoryLimit函数进行设置。以下图为例，在有内存限制参数的加持后，就可以稳定地将堆内存量控制在40MB以下。可以想象，如果没有内存限制这一参数，通过调整GOGC达到这一要求是比较困难的。

# 并发GC实施原理
<a name="gopiJ"></a>
## Go1.5前的STW
在Go1.5之前，GC过程将阻止用户线程的运行，会给应用程序造成一个停顿，被称为Stop The World(STW)，如下图。<br />![image.png](http://pic.kinghno3.top//kinghno3_blog/20240720030929.png)<br />为了避免这种明显的影响，golang引入了并发GC，也就是说GC可以与用户线程并行，这样不会造成应用的暂停，而是只会在一段时间内影响用户线程的CPU资源。并发GC的示意图如下。<br />即便也存在STW，但是非常短暂，只是通知各个线程标记任务开始，准备好写屏障，写屏障具体内容后面说。<br />![image.png](http://pic.kinghno3.top//kinghno3_blog/20240720030942.png)
<a name="nRtnN"></a>
## 并发标记中的用户程序干扰
并发看似很美好，解决了用户线程长时间暂停的问题，但是，如果在GC标记过程中，用户线程修改了对象的引用关系，那么之前的标记结果是否有可能作废呢。<br />预想这样一种情况，在GC标记过程中，有A、B、C三个对象，A为黑色对象，B为白色对象，C为灰色对象，如图。在B未被扫描时，A建立了对B的引用，接着C删除了对B的引用，此时存在黑色对象指向白色对象的情况。<br />那么GC标记程序只能通过A找到B对象，然而A已经被标记为黑色了，GC程序不会再从A出发进行标记了，因此B会漏标，最后被清扫程序错误地清除掉。<br />![image.png](http://pic.kinghno3.top//kinghno3_blog/20240720030956.png)
<a name="ZKyVv"></a>
### 插入写屏障和删除写屏障
为了避免上述的这种情况，我们有两种选择，情况1是杜绝黑色对象指向白色对象，情况2是杜绝删除灰色对象对白色对象的引用后只有黑色对象引用该白色对象的情况。<br />插入写屏障解决了情况1，具体来说，当黑色对象建立对白色对象的引用时，将白色对象B着色为灰色。这样做之后，无论什么情况下B对象都会被GC标记程序所扫描，不会被误伤。<br />删除写屏障则解决了情况2，屏障指的是，当灰色对象删除对白色对象的引用时，将该白色对象着色为灰色。
<a name="YFiHJ"></a>
## Go的混合写屏障
在清楚两种写屏障后接下来对Golang所使用的屏障方案进行分析。Golang使用的是混合写屏障（由Go1.8引入），是在以上两种屏障基础上建立的方案，具体步骤如下：

1. GC开始前，以Goroutine栈为单位扫描，并将栈中的对象着色为黑色。
2. 在GC期间，栈上新创建的可达对象也直接着色黑色。
3. 在堆这个范围中启动插入写屏障
4. 在堆这个范围中启动删除写屏障

我们对以上前两个步骤进行分析：<br />第一步，实际上是将Goroutine栈中的对象放入根集合，从而在GC过程中就可以从这些对象出发进行标记。另外，”以Goroutine为栈为单位扫描”代表着，在该步骤的某个时间点下，有的栈被扫描，有的栈没有被扫描。换句话说，这个时间点下有的栈的对象为黑色，有的栈对象为白色。<br />第二步，由于栈是不参与写屏障的，因此如果不将新对象置为黑色，那么就有可能需要重扫，造成STW。比如，栈上的对象为黑色，在标记过程中指向了一个白色对象，那么就需要进行重扫，才能扫描到这个白色对象。

### 具体场景
![image.png](http://pic.kinghno3.top//kinghno3_blog/20240720031013.png)<br />我直接用以上这张图来囊括多种需要解释的情况。
<a name="MRI5V"></a>
#### 情况1： 为何E对象在栈上创建却是白色
GC过程中（包括GC初始化），栈上的可达节点才会被置为黑色，E明显是不可达的。
<a name="uDIqH"></a>
#### 情况2：首先A引用G，然后F删除对G的引用
第一步：A引用G并不会触发插入写屏障将G对象置为灰色。<br />第二步：但是G和F都在堆种，F删除对G的引用时，会将G置为灰色，保护了G，使之不会被清扫。
<a name="AEGS5"></a>
#### 情况3：D指向H就出现了黑色对象指向白色对象，会导致H误删？
首先，这种情况确实会造成H对象被误删，但事实上，在真实场景中，该情况是无法出现的，因为D无法去引用到一个没有任何可达路径的对象H。

# 内存碎片问题
以一段连续的内存空间为例，其中部分对象由于不可达，被GC程序清除掉，那么就在这段内存空间中留下了空隙，形成外部碎片，降低内存利用率，那么Golang中是怎么解决这个问题的。<br />堆内存以页进行分割，每页大小8Kb，Go构建了一种内存分配单位span，span中有整数个页，因此span大小为8Kb的整数倍，另外每个span中只能分配某种规模的对象，根据可分配的对象规模将span分为了多种类型。 <br />每个span能够分配的对象个数通过对象规模和span大小决定，比如span大小为8Kb，而分配的对象规模为8B，那么能分配的对象个数为`8Kb/8B=1024`个。即使span中部分对象所占的内存被回收，那么该部分内存也不会被浪费，依然会随着程序运行分配给1~8B的对象。<br />当然，会造成内部碎片，比如在8Kb的span中分配1024个1B的对象，这种情况较为极端，不太容易出现。并且，内部碎片相对于外部碎片更容易管理，因为内部碎片只会发生在分配单元内部，比如分配了8B，却只使用了6B，就形成了2B的内存碎片，但是依然可以在分配单元的基础上进行管理。
